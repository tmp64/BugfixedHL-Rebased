Как сервер задаёт таблицу счёта и игровой интерфейс

Таблица результатов игроков — scoreboard. Текст, значки и индикаторы поверх игры — HUD. Правила обмена данными называются протоколом. Новый протокол позволяет серверу настраивать оба представления из одного набора значений.

01

Данные общие, представлений два

Серверный модуль с правилами режима — плагин — задаёт значения и оформление. Игровая программа пользователя — клиент — хранит их и рисует интерфейс. Ей не нужно знать правила конкретного режима, например GunGame, где игрок проходит уровни оружия.

Плагин

Задаёт столбцы, уровни, оружие, тексты и видимость.

→
Сервер

Хранит состояние и отправляет изменения каждому клиенту.

→
Клиент

Обновляет таблицу и HUD из одного хранилища данных.

Владелец значения
Вся игра, игрок или команда. В сообщении это target.
Ячейка
Значение для одного владельца в одном столбце: например, уровень игрока.
Ключ
Короткое имя, например level. Плагин использует имена; сервер назначает числовые номера — id.
Элемент
Один объект HUD: строка, значок, индикатор или лента значков.
Шаблон и вариант
Текст с местами для подстановки данных — шаблон. Один из альтернативных текстов элемента — вариант.
Ссылка на значение
Имя, по которому клиент берёт ячейку или вычисленное значение для элемента.

Набор настроек таблицы и её столбцов называется схемой. Столбец может быть скрыт, но его данные всё равно доступны для сортировки и HUD.

Основание: документ, §2, §5.1, §8.1.

02

Что именно идёт по сети

Байт — единица данных из восьми двоичных разрядов, или битов. Один байт хранит число от 0 до 255. Набор битов-переключателей называется битовой маской. Ниже байты записаны в шестнадцатеричной системе: 0x03 означает число 3, 0xFF — 255.

Сообщение BhlScoreДо 192 байт, включая код операции
1 байт: что сделатьОстальные байты: данные операции

Это двоичный формат. Одно сообщение содержит одну операцию. Движок доставляет его надёжно одному клиенту через режим MSG_ONE. Ограничение 192 байта относится к содержимому BhlScore; служебные заголовки сети здесь не считаются.

Первый байт — код операции (op). Поле — отдельная часть сообщения. Тип поля определяет его размер и способ чтения:

ТипРазмерСмысл
byte1 байтЦелое 0…255.
short / word2 байтаЦелое −32 768…32 767 / 0…65 535.
long4 байтаЦелое −2³¹…2³¹−1; в поле видимости те же 32 бита служат переключателями.
stringДлина текста + 1Текст в UTF-8 — кодировке с разным числом байтов на символ. Конец обозначает нулевой байт 00, называемый NUL.

В многобайтовом числе младший байт идёт первым — порядок little-endian: число 300 передаётся как 2C 01. Лимиты текста считаются в байтах без завершающего NUL, а не в буквах.

Выберите операцию. В записи ниже поле:тип указывает имя и тип, квадратные скобки — повторяющуюся группу.

Values · значения ячеек

до 192 байт

Передаёт одну или несколько групп ячеек. Каждая группа относится к игре, игроку или команде.

target — владелец значенияcount — число ячеекcolumn — номер столбцаtype — тип значенияlen — длина данныхpayload — данные значения
op:byte → [target:byte → count:byte → [column:byte → type:byte → len:byte → payload:len байт] × count] до конца сообщения

Новый тип можно пропустить по длине len. Для неизвестного типа ячейка очищается. Остальные ячейки сообщения продолжают читаться.

Какими бывают значения ячеек и элементов списка

Каждое значение имеет обёртку type:byte → len:byte → payload. Длина len учитывает только данные после этих двух байтов. «Текущий / максимальный» далее сокращены до cur / max.

Тип значенияКод / длина данныхДанные
Пусто — None0 / 0Очищает ячейку.
Число — Int1 / 1, 2 или 4Целое со знаком, включая однобайтовый вариант.
Текст — Text2 / 1…32Одна строка с NUL.
Значок — Icon3 / 2…64Имя готового изображения клиента — спрайта — и подпись: две строки с NUL. Само изображение не передаётся.
Прогресс — Progress4 / 2 или 4cur, затем max: два byte или два word.
Часы — Clock5 / 5ms:long — миллисекунды; flags:byte — настройки. Бит 0: идут; бит 1: обратный отсчёт. Клиент продолжает отсчёт сам.

target: 00 — игра; 01…40 — игроки 1–64; 81…C0 — команды 1–64. Столбец FF вместе с None очищает все ячейки владельца. Список — именованная последовательность значений всей игры; длинный список делится между сообщениями.

Все восемь форматов одной таблицей

Поля перечислены в порядке передачи после op:byte. Набор битов-переключателей называется битовой маской; такую роль играют поля flags, visible и hide. Текст с местами для подстановки данных называется шаблоном.

ОперацияПоля после кода операции
00 Resetversion:byte
01 Configflags:word → title:string → tag:string
02 Columnid:byte → display:byte → flags:word → width:byte → sort:byte → key:string → title:string → host:byte
03 Values[target:byte → count:byte → [column:byte → type:byte → len:byte → payload:len байт] × count] до конца
04 Listid:byte → total:byte → start:byte → key:string → [type:byte → len:byte → payload:len байт] до конца
05 Elementid:byte → kind:byte → flags:word → x:short → y:short → align:byte → place:byte → parent:byte → gap:byte → color:4 byte → font:byte → select:string → value:string → list:string → count:byte → [id:byte → value:short] × count. Для удаления: только id и kind = 0.
06 Templateid:byte → variant:byte → text:string
07 HudStatevisible:long → hide:word

Передача всего текущего состояния называется полной синхронизацией. После неё сервер отправляет только изменения.

Порядок отправки, ограничения и защита от ошибок

Сначала сброс, затем определения и данные, в конце — тексты и видимость:

Reset→Config / Column→List→Values→Element→Template→HudState

После входа синхронизация начинается примерно через 0,5 с. Бюджет — около 512 байт на клиента за кадр, затем при его исчерпании пауза около 0,1 с. Далее отправляются изменения; несколько записей одной ячейки за кадр сворачиваются в последнее значение.

Лимиты: 32 столбца, 32 элемента, 8 списков по 64 значения, 8 вариантов текста на элемент, 16 подстановок на шаблон. Текст шаблона — до 188 байт: 1 + 1 + 1 + 188 + 1 = 192 с заголовком и NUL. Слишком длинный шаблон отклоняется целиком.

Неизвестные операции игнорируются. Неверный тип или повреждённые данные значения очищают ячейку. Если Values оборвалось, уже применённые ячейки сохраняются. У фиксированных операций можно добавлять поля в конец; Values и List расширяются новыми типами либо операциями.

Основание: документ, §4–5. Это форматы Draft 2.

04

Как данные превращаются в HUD

Элемент — один объект на экране. Сервер задаёт его вид, положение, цвет, размер текста и источник значения. Есть четыре вида:

Строка — Text

Место, отрыв, время или другой текст.

Индикатор — Meter

Прогресс точками или полосой.

Лента — Strip

Последовательность значков, например уровни оружия.

Значок — Icon

Изображение с необязательной подписью.

Текст пересчитывает клиент

Шаблон — текст с подстановками в фигурных скобках. Ссылка внутри скобок выбирает ячейку по ключу либо вычисляемое клиентом значение с @.

Например, @rival — имя ближайшего соперника впереди; @pass — сколько единиц счёта нужно для обгона. Здесь единица счёта соответствует одному убийству.

До обгона {@rival}: {@pass|# убийство|# убийства|# убийств}

Вертикальная черта | разделяет формы слова; # заменяется числом. Имя и число подставляются из данных.

3
До обгона Соперник: 3 убийства

Если обязательного значения нет, вся строка скрывается. Подстановка вида {key?} допускает отсутствие значения.

Чьи данные и чьи тексты

Игрок видит свои данные; наблюдатель — данные того, за кем следит. Поиск ячейки: игрок → его команда → вся игра, до первого найденного значения. Без наблюдаемого игрока доступны только общие ячейки.

Язык и видимость принадлежат смотрящему клиенту. Сервер может отправить русскому наблюдателю русский текст с данными другого игрока.

До восьми альтернативных текстов элемента называются вариантами. Поле select выбирает их по числу 0–7, например по фазе матча. Это не программный код: условия режима остаются в плагине.

Имя готового перевода — токен локализации, например #BHL_HUD_Place. Его перевод уже хранится у клиента. Плагин также может отправить собственный готовый текст на языке пользователя.

Положение и показ элементов

Для положения относительно экрана координаты x / y передаются как доля размера экрана, умноженная на 8192. Специальное значение −8192 означает центр; y = 205 — примерно 2,5% высоты от верхнего края. Выравнивание выбирает, какую точку элемента привязать к позиции.

Можно размещать элемент у другого элемента, рядом с числами здоровья и боезапаса либо в верхней части таблицы. Элемент появляется только при разрешённой видимости, подходящем состоянии игры и наличии содержимого. Показ надписи в заголовке таблицы не зависит от настройки экранных элементов HUD.

Сервер может попросить скрыть таймер, строку следующей карты, дополнительные таймеры и нижние индикаторы скорости. Настройка пользователя, отключающая серверные элементы, отменяет эти запросы.

Совместимость: клиент выбирает возможности

Набор битов-переключателей — битовая маска возможностей — передаётся серверу под именем _bhl. Бит 0, ScoreboardV1, разрешает получать данные; бит 1, HudV1, сообщает, что клиент рисует элементы HUD. Ниже предполагается новый активный сервер с таблицей и HUD.

_bhl3

Данные приходят. Новая таблица и серверные элементы включены. Плагин отключает заменённые ими собственные надписи.

Управляющие настройки: hud_scoreboard_custom и hud_server_elements. Старый клиент не получает BhlScore; новый клиент на старом сервере сохраняет стандартный интерфейс. Бит HudV1 сам по себе не разрешает отправку: он имеет смысл только вместе со ScoreboardV1.

Основание: документ, §3, §8, §10–11.

1

Восстановить данные после очистки клиентом

При переинициализации изображения — событии VidInit — клиент очищает хранилище. Но среди причин полной синхронизации этого события нет. Если сервер не выполняет повторную подготовку интерфейса и возможности не меняются, состояние нечем восстановить.

Уточнить: сохранять данные при таком событии либо явно описать запрос и гарантированный запуск повторной синхронизации.

Документ: §3.2, §5.3, §6.1; строки 99–103, 658–665, 705–707.

2

Безопасно заменить уже видимый элемент

Новое определение сохраняет прежние шаблоны на клиенте. Определение и новые тексты могут прийти в разных кадрах из-за лимита отправки. Если старый бит видимости включён, новое оформление может временно использовать старый текст.

Уточнить: сначала скрывать или удалять заменяемый элемент либо применять определение и тексты совместно, только после их получения.

Документ: §4.3 Element / HudState, §5.2; строки 471–474, 507–509, 641–654.

3

Определить время часов при поздней отправке

Клиент запускает часы от момента получения. Не описано, как сервер пересчитывает их значение после задержки или при подключении нового игрока. Для отсчёта, заданного минуту назад, нельзя просто повторить исходное число.

Уточнить: хранить время установки и перед отправкой вычислять актуальное значение, включая остановку обратного отсчёта на нуле.

Документ: §4.3 Clock, §5.1–5.3, §9.2; строки 367–371, 612–617, 658–665, 1518–1519.

Ещё один граничный случай: ссылка на собственное значение

Поле value допускает встроенные ссылки, а @value обозначает это же поле. Для value = @value и value = ^@value не задано завершение вычисления. Следует запретить такие привязки или считать цикл отсутствующим значением. Основание: §4.3, §8.10–8.11, §9.2.

Вывод ревью: протокол можно объяснить как «определения + значения + тексты + видимость». Перед реализацией нужно закрепить восстановление состояния, порядок замены элементов и поведение часов. Проверка в игре остаётся отдельным этапом.
